01

Process

Six steps, in this order, every time. The step I never skip is the first one: if I can’t name the number a design should move, I’m not ready to design it.

  1. 01

    Frame the problem

    Name the business metric to move, and the guardrail metric I refuse to hurt.

    OutputA one-page brief with the hypothesis
  2. 02

    Understand behaviour

    Interviews, analytics, support tickets, and teardowns of how others solve it.

    OutputAn insight summary in plain language
  3. 03

    Map the flow

    User flows, information architecture, and every edge case: empty, loading, error, and offline.

    OutputFlow diagrams in FigJam
  4. 04

    Design and prototype

    System components first, then high-fidelity screens and a clickable prototype.

    OutputA Figma prototype people can test
  5. 05

    Test and refine

    Usability tests on the riskiest moment, and an experiment plan for what can only be learned live.

    OutputFindings and an A/B test plan
  6. 06

    Ship and measure

    Handoff in Dev Mode, a QA pass with engineers, and events tracked from day one.

    OutputA tracking plan and launch checklist
02

Design systems

I treat a design system as a product. It has users (designers and engineers), a roadmap, and a definition of done. Its job is to make the right choice the easy one, so teams ship faster without the product drifting apart.

Five layers I build and maintain

  1. 1
    Tokens

    Colour, type, spacing, radius, elevation, and motion as named variables, each with a light and dark value.

  2. 2
    Components

    Buttons, inputs, cards, and navigation built with variants and properties that match how engineers write them.

  3. 3
    Patterns

    Proven combinations like onboarding steps, paywalls, empty states, and checkout, so teams don’t redesign them each time.

  4. 4
    Documentation

    When to use each piece, when not to, accessibility notes, and do and don’t examples.

  5. 5
    Governance

    A contribution process, versioning, and a changelog, so the system grows without breaking what’s shipped.

How I build systems in Figma

  • Variables and modes

    Colour, spacing, and radius live as variables, with a light and dark mode, so a theme switch is one click.

  • Variants and component properties

    States, sizes, and icons are properties, named the way engineers name props in code.

  • Auto layout everywhere

    Components resize with their content, so the mobile layout is the desktop one reflowed, not a second design.

  • Clear naming

    Component / Variant / State, for example Button / Primary / Disabled, so anyone can find what they need.

  • Documentation pages

    Usage, do and don’t examples, and accessibility notes sit beside each component.

  • Dev Mode annotations

    Specs, tokens, and behaviour are annotated where engineers look for them.

03

Accessibility by default

Accessibility isn’t a final check. I build it into the first component, so every screen made from the system inherits it, including on this site.

  • ContrastText meets WCAG AA: 4.5:1 for body text, 3:1 for large text and UI parts.
  • Touch targetsAnything tappable is at least 44 by 44 pixels.
  • Visible focusEvery interactive element shows a clear focus ring for keyboard users.
  • Reduced motionAnimations switch off for people who ask their device for less motion.
  • Never colour aloneStatus always has a label or icon too, not just red or green.
  • Plain languageErrors say what happened and what to do next, without jargon.
04

Working with engineers and product managers

Good design dies in handoff. These habits keep what ships close to what was designed, and keep everyone moving.

  • Specs engineers can build from

    Every screen ships with its states, spacing, and behaviour annotated in Dev Mode, not left to guesswork.

  • The states checklist

    Empty, loading, error, success, offline, and long-content states are designed before handoff, not discovered in QA.

  • Design QA before release

    I review the build against the design with the engineer and log fixes in priority order.

  • Decisions written down

    Why we chose an option, and what we rejected, lives next to the design, so nobody re-argues it in a month.
